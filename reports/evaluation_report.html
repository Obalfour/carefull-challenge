The result shows the design works on these patterns, not how it generalizes.

The errors are systematic, not random
Most rule false positives belong to Robert Chen and Frank Martinez: active users whose spending is high and variable by design (travel, golf, monthly transfers to family). Amount-based rules cannot tell "unusual for a statistic" from "unusual for this person"; the profile can. The money-mule rule is the only one that is precise on its own.

How the LLM removed them

  • Robert Chen – BRITISH AIRWAYS PNR XKJD92 ($2,340, Amount spike, Weekly overspend): “The transaction is a large travel expense, but it is consistent with the user's stated lifestyle of frequent travel and is supported by recent evidence of international activity (an Uber trip in London).”
  • Helen Park – IKEA PORTLAND OR ($580, Amount spike): “The transaction at IKEA is consistent with the user's recent move to a new condo and her established shopping history in Portland. The amount is reasonable for home furnishings and does not indicate fraud.”
  • Frank Martinez – ZELLE TO ISABELLA MARTINEZ ($500, Amount spike): “While the $500 transfer to Isabella Martinez is larger than usual, it is consistent with Frank's established behavior of being generous with his family. Given his stable pension income, this is likely a planned gift rather than fraudulent activity.”

Confidence and uncertainty handling

  • LLM confidence ranged from 0.70 to 1.00 (median 0.95); 0 transactions went to human review.
  • Because every validated decision was correct, this data cannot tell whether confidence is calibrated. The low-confidence path (< threshold → suspicious + human review) and the LLM-failure fallback (keep the rule label + review) were not exercised by real cases here.

What could fail on new data

  • Rule recall is the ceiling. The LLM only sees what rules flag. A slow exploitation with flat amounts (e.g. $300 every week) would not trip the spike rule.
  • Weekly rule latency. It uses the calendar week's total, so it fires up to 7 days late; a rolling 7-day window is needed in production.
  • Alias resolution is permissive. The "same initial" rule would merge Marco and Maria Martinez.
  • Biographies help a lot. "Wife Patricia manages household expenses" explains Robert's transfers. Users with thin profiles will produce more false alarms.

Model choice
Validation is a reading-comprehension task over ~2k tokens of structured context, and the lite model already makes no errors here, so a bigger model can only add cost and latency on this data. A larger model is worth testing on harder, ambiguous cases (thin profiles, partial patterns), where the comparison would actually discriminate.

Where to optimize

  • Lower the flag rate first. 38 of 70 validations were benign. Tightening the rules (as with the weekly rule: 159 → 70 flags with no recall loss) saves more than any model change.
  • One call per incident, not per transaction. Helen's 12 foreign purchases are one story; validating the pattern once would cut those calls by ~10x.
  • Batch API for the non-urgent weekly checks (50% cheaper) and prompt caching for the fixed system prompt and the user's profile, which repeat on every call of a user.
  • At these prices the LLM is not the main cost driver; analyst time on false alarms is. Keep the model that minimizes false alarms, not the cheapest one.
